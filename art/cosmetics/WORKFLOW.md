# Cosmetics workflow

Read this first in every cosmetics session. It is the only process doc; item details live in each `brief.md`, progress lives in `INDEX.md`.

## Where things live

```
docs/tessera-items-per-level.xlsx   design source: names, unlock levels, descriptions
art/cosmetics/
  WORKFLOW.md                       this file
  INDEX.md                          tracker: every item + status (generated, edit Status only)
  titles.md                         titles: text only, no art
  _shared/                          style.md (research, palette, rules), shared bases, preview scene, templates, scaffold.py
  <kind>/<item-id>/                 one folder per item
    brief.md                        look + prompt + notes
    source.blend                    Blender kinds only
    preview.png                     512px render or SVG snapshot, used for review and in the menu
public/cosmetics/<kind>/<item-id>.glb|.svg   the only file the game loads
```

Sources stay in `art/` (never deployed); `public/` gets only the small runtime file.
Item ids are kebab-case and never change, so renaming an item in the sheet never breaks a path.
After changing the spreadsheet, run `py art/cosmetics/_shared/scaffold.py`: it adds new items and keeps statuses.

## Pipeline per kind

| Kind | Made in | Runtime file | Budget |
|---|---|---|---|
| characters | Blender, generated by `build.py` on `_shared/charlib.py`; two variants (a, b) | `<id>-a.glb`, `<id>-b.glb` | 3,000 to 5,000 triangles per variant |
| companions | Blender | `.glb` | ≤ 800 triangles, one 2-4 s idle loop |
| plinths | Blender, on the shared hex base | `.glb` | ≤ 1,200 triangles |
| banners | SVG | `.svg` | readable at 24 px |
| surrounds | SVG, faceted shapes for the low-poly look | `.svg` | readable at 40 px |
| dice | Blender, on the shared die base; flat face SVG made from it | `.glb` + `.svg` | ≤ 300 triangles; face readable at 32 px |

Rules for every kind:
- Colours come from the palette in `_shared/style.md`, so everything matches.
- Anything that should show the player's colour uses the material named `player` (3D) or `currentColor` (SVG). The game tints it.
- Flat shading, no image textures in 3D (vertex colours or palette materials only). Files stay tiny for free hosting.
- 3D: origin at the feet / centre of the base, Y up, 1 unit = character height, transforms applied, export glTF binary.

## Phase 0: once, built along with the first items

Each shared base is made by the first item that needs it, then reused:

1. Palette: in `_shared/style.md` (done).
2. Character building blocks: done (`_shared/charlib.py`, set by the Captain). The victory pose comes later on the same rig.
3. Preview scene: done (`_shared/preview.blend`).
4. Plinth base, a hex tile (radius 1) with marked spots for the character and companion: built by Meadow.
5. Die base, a bevelled low-poly cube (size 1, origin in the centre) with pips as separate objects and materials `body`, `pip`, `edge`: built by Ivory. Every dice skin is this die with its own materials and at most small shape changes (carved runes, mosaic tiles). Physics for the later 3D roll uses a plain box, so the shape can vary freely.
6. SVG templates (banner flag, surround ring with a fixed inner hole, flat die face): built by Plain pennant, Plain and Ivory.
7. Game side: load `.glb` with drei `useGLTF`, tint the `player` material, show the default item while loading; banner SVG becomes a texture on one shared flag mesh. Done once the Captain is approved, as the end-to-end test.

## Per item

1. **Brief** (status `brief`): research and fill every section of `brief.md`, then delete the template marker line. `characters/captain/brief.md` is the example to match. Research covers three things: low-poly references for this kind of item, the real-world history of the thing, and how it fits Catan and our game, ending in our interpretation. Design choices are a table with a reason for each choice and a "Not this" row, so items don't borrow each other's signatures. The user reads the brief and approves it before anything is built. Reading markdown is cheap; rebuilding a model is not.
2. **Build:**
   - Blender kinds: follow the brief's Blender prompt, starting from the right base in `_shared/`. Use the Blender MCP (`execute_blender_code`) and check with `look` at max_size 512 only at the brief's checkpoints. Save as `source.blend`. Don't use `generate_3d`: it costs credits and isn't low-poly.
   - SVG kinds: write the SVG from the template.
   - Dice: build the 3D die first, then the flat face SVG for the CSS dice from the same `body`/`pip`/`edge` colours, so both versions match. The CSS dice use the SVG until the 3D roll exists.
3. **Preview** (status `built`): render `preview.png` and tick the brief's acceptance list.
4. **Review** with the user from the preview: one correction round, then it's approved or parked.
5. **Export** to `public/cosmetics/<kind>/<id>.<ext>` and add the item to the catalog in `src/shared/cosmetics.ts`. Status `approved`, and `in game` once it shows in the app.

## Who does what

| Task | Agent | Why |
|---|---|---|
| Brief (research + design) | Sonnet subagent, 3 to 5 briefs per run, given this file, `_shared/style.md` and the Captain brief as the example | Web research and writing are routine once the example exists |
| First item of each 3D kind (Captain, Meadow, Ivory) | main session (Opus) | Builds the shared base and sets the look; needs visual judgement |
| Later characters, companions, plinths, dice | Sonnet subagent with the Blender MCP, then the main session reviews the preview | The base and the brief carry most of the decisions |
| Banners, surrounds, flat dice faces (SVG) | Sonnet subagent | Simple, text-only output |
| Review against the brief | main session | One `look` or one image per item |

If a Sonnet build misses the brief twice, the main session takes over that item.

## Order and budget

- Go by level: the free items first, then levels 1 to 20 (batch 1). Levels 21 to 100 come later, a few per session.
- Start a session with: "Read art/cosmetics/WORKFLOW.md and INDEX.md, then do the next N items." Nothing else needs reading.
- Write briefs a batch ahead of building, so the user can approve several at once.
- Blender work needs looking at renders: keep `look` small (512) and look once per checkpoint, not after every step.
